# 原始需求与环境事实

## 1. 需求原文（用户原话，未改写）

> 二次开发需求：将这个工具转变成批量转录并利用 AI 翻译成中文。
> 输入：多个 YouTube 视频链接
> 输出：每个视频输出两份文档，一份是原稿，一份是中文译稿，都是 txt 格式。注意，AI 还需要优化格式，但必须保持原文
> 约束：下载视频时，默认下载最低清晰度的视频；本机已经安装了 whisper，当然需要检查下，转录时用 GPU 处理，一般来说视频都是英文，可以试用 small 级别的 whisper（我不知道长视频是否需要用到 middle，你自行决定）。

## 3. 硬技术约束（必须在设计阶段体现）

1. **whisper 不能翻译成中文**：openai-whisper 的 `--task translate` 只输出**英文**译文，中文译文必须由 LLM 或机器翻译完成。所以"AI 翻译"是必需组件，不是可选优化。
2. **长视频与模型大小无关**：whisper 内部按 30s 窗口滑动处理，1 小时视频用 `small` 不会因为"长"而必须换 `medium`；时长只影响耗时与幻觉累积概率。`medium` 提升的是准确率，不是长度能力（另：级别名是 `medium`，没有 `middle`）。
3. **转录只要音频**：视频最低清晰度往往带低码率音轨，且要额外下载视频轨；对纯转录任务，`bestaudio`（m4a/webm）更小更快，结果等价。是否坚持"下载最低清晰度视频"需要用户确认。
4. **GPU 阶段必须串行**：单卡 + 低空闲显存，转录任务应串行（并发度 1）；翻译是纯文本，可与转录重叠，但并发受 API 速率/本地模型显存限制。
5. **长文本必须分块翻译**：1 小时英文 ≈ 9k 词 ≈ 12–13k tokens；任何在线模型的单次上下文与输出上限、以及"术语一致性"要求，都意味着要按段分块 + 携带术语表/前文摘要，而不是一次整篇送入。
6. **"保持原文"需要一个可判定的定义**：LLM 做"格式优化"时的改写风险需要用校验（机械规则 + 可选 diff 校验）兜住，否则原稿会被悄悄改写过。

## 5.1 其余默认值（已按建议采纳，可在实现中调整）

- 原稿零 LLM 改写；译稿按段落 1:1 对齐。
- 输出：`<输出根目录>/<视频标题>/transcript.en.txt` + `transcript.zh.txt`；UTF-8(无 BOM) + LF；无时间戳；段间空行；已存在则跳过（可配 `overwrite`）。
- 中间产物：`<输出根目录>/<视频标题>/.work/`（音频、分块、`segments.json`、`zh.blocks.json`、`usage.json`），用于断点续跑与人工校对，不属交付物。
- 非英文/无语音：仍转录但译稿标注源语言；无语音标记跳过；批次结束输出汇总清单。
- 并发：下载 2、转录 1（GPU 串行）、翻译 2；单批 ≤50 条、单视频 ≤3 小时，可续跑。
- 第一期不做：说话人分离、手动改稿后重译、词级时间戳。

## 6. 模型选择（已由开发者授权自行决定，结论如下）

- **默认 `small`**（英文、GPU、fp16）：1 小时音频约 3–8 分钟，WER 对"可读文稿"足够；显存约 1–2 GB。
- **升级条件**：抽样人工比对发现明显错误（专有名词、口音、术语）→ 对该视频（或整批）切 `medium`；不建议默认 `large`（慢 2–3 倍，收益递减）。
- **可选提速路线（需安装新依赖，待用户同意）**：`faster-whisper`（CTranslate2）在 8 GB 卡上可再快 3–5 倍并支持批处理；`whisperX` 提供词级时间戳与更好的长音频切分。第一期不引入，若吞吐成为瓶颈再评估。
- **长视频注意**：关闭 `condition_on_previous_text`（或设置 `carry_initial_prompt=False`）以降低重复/幻觉循环风险，并按 10–20 分钟切片转录后在文本层拼接（同时在片段边界保留 2–5 秒重叠以免丢词）。

## 8. 追加需求（2026-09-17，开发者）——长链路日志文件

### 需求原文

> 考虑整体业务链很长，必须有一个 .log 文件，随时记录转录过程中发生的关键事件日志和错误信息，方便出错时即时排查

### 技术含义与已定方案（详见 change 的 design.md 第 8 节与 implementation-notes.md）

| 维度 | 决定 |
| --- | --- |
| 文件数量 | **一个全局轮转日志**：`<app_dir>/logs/transcribe.log`（+ `.1`…`.4`，5MB × 5 ≤ ~25MB）；不另建每视频日志，靠 `groupId`/`runId` 字段检索单链路 |
| 实现方式 | `tracing` 追加一个文件层（`tracing-appender` 滚动 writer），使**现有全部 `tracing::*` 调用自动落盘**（yt-dlp 运行摘要、二进制安装、配置副作用等） |
| 关键事件 | 稳定事件码（`stage.change`/`audio.download.*`/`chunk.*`/`whisper.*`/`merge.*`/`transcript.*.ok`/`translate.block.*`/`video.done`/`video.skip`/`video.fail`/`batch.done` 等），每行含 ISO 时间、level、event、`run`/`group`/`stage` 字段 |
| 即时性 | 追加写 + 每行 flush（`tracing-appender` 的非阻塞 writer），崩溃后已写事件不丢 |
| 错误 | 每个 `errorCode` 至少一行 ERROR 级日志（含 code/stage/exit code/stderr 摘要截断） |
| 脱敏 | 不得出现 `ai.apiKey`、Cookie、Bearer、请求头的值；yt-dlp 敏感 flag 只记存在性布尔（沿用 `RunLogSummary`）；失败响应片段仅记截断内容 |
| 详细模式 | `logging.verbose`（默认 `false`）开启后额外记录工具逐行原始输出（yt-dlp/whisper/ffmpeg） |
| 失败降级 | 日志目录不可写时仅告警一次（`logWriteFailed`），**不阻断**转录 |
| UI 可达 | `transcription_probe` 返回日志路径；设置/关于页显示路径与大小并提供"打开日志"，Logs tab 提供"打开日志文件" |
